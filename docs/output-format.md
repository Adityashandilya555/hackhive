# Output format

What `hackhive solve` writes for one plan, key for key. The organisers' slides win every conflict (slide 8 is the format); every edge case is decided in [`decision_conventions.md`](decision_conventions.md). The JSON schemas are generated from `src/hackhive/contracts.py` into `schemas/` (`uv run python -m hackhive.contracts`).

For a plan with id `<plan_id>`, `hackhive solve <plan> --out <dir>` writes:

| File | When | What |
|---|---|---|
| `<plan_id>.json` | only when the status is `ok` or `submitted_strict_only`, under the problem-statement settings | the slide-8 **submission** (the only file the organisers read) |
| `<plan_id>.sidecar.json` | always | our **sidecar**: status, reason, violations, bounds, cost, settings, provenance, warnings |
| `<plan_id>.png` | whenever the plan loaded | the overlay (#17) |

File names use `solve.file_stem(plan_id)`: characters other than `A-Z a-z 0-9 _ . -` become `_`, so an organiser id like `A/B` can't write outside `--out`. The submission keeps the id verbatim.

## 1. The submission (slide 8)

Exactly these keys; any other key is rejected (`extra="forbid"`, `contracts.Submission`).

**Units and frame:** metres, origin lower-left, y up. ResPlan is already y-up, so dev plans are `(x, y) ÷ scale`. An organiser plan is written in the frame its given nodes are in (sidecar `frame`); nothing is transformed back.

**Rounding (T6):** every coordinate (hub `location`, every polyline point) has at most **4 decimals** (0.1 mm, below the checker's 1 mm tolerance). Each vertex is rounded once and a piece's shared coordinate is copied from the vertex before it, so every piece of a polyline is exactly horizontal (`y` equal) or exactly vertical (`x` equal). `length_m`, `ring_length_m` and `reported_metrics` are then recomputed from the rounded polylines, so they always match them.

| Key | Type | Meaning |
|---|---|---|
| `plan_id` | string | the plan's id (organiser ids as given; ResPlan dev plans `PLAN_<id>`) |
| `units` | `"m"` | always metres |
| `hubs` | array of hub | one per hub, `H1`, `H2`, … in output order |
| `hubs[].hub_id` | string | plan-global hub id |
| `hubs[].room_id` | string | the eligible room the hub sits in; always one of its `assigned_rooms` |
| `hubs[].location` | object `{"x": number, "y": number}` | the hub point, ≥ 0.5 m from walls (slide 3 rule 6) |
| `hubs[].assigned_rooms` | array of string | the hub's zone: **its own `room_id` first**, then the other rooms by id |
| `hubs[].assigned_nodes` | array of string | the nodes of those rooms, **sorted by id** |
| `hubs[].closed_sequence` | array of string | the ring order: `[hub_id, every assigned node once, hub_id]` |
| `hubs[].route_segments` | array of segment | one per consecutive pair of `closed_sequence`, **in ring order** (count = len − 1) |
| `…route_segments[].from` | string | `closed_sequence[i]` |
| `…route_segments[].to` | string | `closed_sequence[i + 1]` |
| `…route_segments[].length_m` | number | the polyline's length |
| `…route_segments[].polyline` | array of `[x, y]` | corner points only; starts at the `from` point and ends at the `to` point (within 1 mm); the next segment starts where this one ends |
| `hubs[].ring_length_m` | number | sum of the ring's `length_m`, return leg included |
| `reported_metrics.hub_count` | integer | number of hubs |
| `reported_metrics.total_length_m` | number | sum of every `ring_length_m` |

Note the two point shapes: `location` is an object, polyline points are arrays. The organisers' checker ignores `length_m`, `ring_length_m` and `reported_metrics` and recomputes them (C42); ours are still always consistent.

## 2. The sidecar (`<plan_id>.sidecar.json`, `contracts.Sidecar`)

Everything that is not part of the submission. Always written, also when there is no design.

| Key | Type | Meaning |
|---|---|---|
| `plan_id` | string | as in the submission (for `input_error`: the file's own `plan_id`, else its stem) |
| `status` | string | one of the four statuses in section 3.1 |
| `reason` | string or null | why there is no submission (`infeasible`, `input_error`), in words |
| `frame` | `"identity"`, `"flip_y"`, `"origin_shift"` or null | the organiser node frame the geometry was moved into (#38); null when no plan loaded |
| `violations` | array of violation | the checker mirror's findings on the design |
| `violations[].rule` | integer | slide 3 rule number (1-6) |
| `violations[].severity` | `"error"` or `"strict"` | `error`: a certain slide break; `strict`: only our conservative reading (#46) |
| `violations[].message` | string | in words |
| `violations[].ids` | array of string | the room / node ids involved |
| `violations[].hub_id` | string or null | the hub involved |
| `violations[].where` | array of `[x, y]` | metres; the overlay draws these in red |
| `bounds` | object or null | hub-count bounds (`contracts.Bounds`) |
| `bounds.k_lb` | integer | lower bound max(⌈area / 100⌉, ⌈nodes / 5⌉) (C7) |
| `bounds.k_found` | integer or null | hubs in the design (null without a valid one) |
| `bounds.proof` | `"exhaustive"`, `"lb_met"`, `"greedy"` or `"none"` | how `k_found` is known to be minimal: full enumeration; equal to `k_lb`; the greedy fallback (#49, planned); not known |
| `cost` | object or null | the design's metrics (`contracts.CostBreakdown`), strict reading |
| `cost.H` | integer | hubs |
| `cost.L` | number | total cable length, m |
| `cost.X` | integer | crossing points |
| `cost.O` | number | overlap length, m |
| `cost.B` | integer | bends |
| `cost.J` | number | L + 5X + O + 0.5B (section 4) |
| `cost.area_gap` | number | max − min of the hubs' assigned eligible area, m² (0 for one hub) |
| `hubs` | array | per-hub share (`contracts.HubMetrics`): `hub_id`, `area_m2`, `n_nodes`, `L`, `X`, `O`, `B` |
| `settings` | object | the `Constraints` used: `max_area_m2`, `max_nodes`, `hub_wall_clearance_m`, `tolerance_m`, `grid_m`, `flip_y`, `origin_shift`, `interior_windows_as_doors`, `zone_links_via_excluded`, `route_through_other_rooms`, `cost_weights` (`length`, `cross`, `overlap`, `bend`) |
| `settings.is_problem_statement` | boolean | true only for the organisers' preset; written, never read (recomputed on load; a value that disagrees with the settings is an error). `false` means a WHAT-IF run, which has no submission |
| `provenance` | object | `input_path`, `input_digest` (`sha256:…` of the input file), `version` (hackhive's) |
| `warnings` | array of string | section 3.2 |
| `folded_parts` | array | living slivers folded into a neighbour (C38): `room_id`, `into_room_id`, `area_m2` |

## 3. Statuses and warnings

### 3.1 Status

| Status | When | `<plan_id>.json` written? |
|---|---|---|
| `ok` | the design has no violation at all | yes |
| `submitted_strict_only` | the design's only violations are `strict` (our conservative readings). An invalid or missing plan scores zero, so it is still submitted, flagged | yes |
| `infeasible` | no design without an `error`: no zoning can be built (a room > 100 m², a zone with no hub-capable room, …), too large for exact zoning, the grid or routing failed, or the design breaks a rule; `reason` says which | no |
| `input_error` | the plan file can't be read, or fails the frame check (#38); `reason` says why | no |

With a what-if setting (`settings.is_problem_statement: false`) nothing is written as a submission, whatever the status.

### 3.2 Warnings

Warnings never change the status or stop a submission; they explain it.

| Warning (example text) | When | Submission? |
|---|---|---|
| `R03 (bedroom): node N2 clearance 0.42 m < 0.5 m` (node `clearance_m < 0.5`) | a node's room can't fit a point 0.5 m from walls; the node stays at its max-clearance point (A2, A9) | unaffected |
| `R07 (1.2 m²) folded into R01: too narrow for a node at the wall clearance (C38)` | a ResPlan living sliver was folded into a neighbour (generator only); also in `folded_parts` | unaffected |
| `H1: wall_clearance_only` | no grid point in the hub's room is ≥ 0.51 m from the whole room outline, so the hub is only ≥ 0.51 m from walls (#46 Q3) | unaffected (rule 6 may add a `strict`) |
| `reported H1 ring_length_m … m, recomputed … m (the organisers recompute it, C42)` | a written submission's `length_m`, `ring_length_m` or `reported_metrics` disagree with its polylines by > 1 mm (read back by `submit`) | still written |
| `WHAT-IF: area cap 120 m² (problem statement: 100 m²). Never written as a submission (C29).` | the run used a what-if setting (#30) | never written |
| `plan_id 'A/B' isn't a safe file name: files are written as A_B.*` | the id needed `file_stem` | unaffected |
| `R04 (bedroom): no given node (slide 2: one per room)`, or `2 given nodes in one room` | organiser input with a room-set mismatch | unaffected |
| `R05 (living) lies 25% outside inner` | an eligible room more than 20% outside `inner` | unaffected |
| `room > 100 m²` | a room over the area cap; the status is `infeasible` | no |
| `greedy_zoning` | **planned, not yet emitted** (#49): the greedy fallback zoning for > 16 eligible rooms in one component | would be written, with `proof: "greedy"` |

## 4. J and the metrics

Ranking (slides 3, 6, 7): fewest hubs H first, then the lowest

**J = L + 5X + O + 0.5B**

(metres; the weights are `contracts.ORGANISER_WEIGHTS`, the organisers' starting values, #48), then the smaller assigned-area gap. Every metric is recomputed from the polylines only, at 1 mm tolerance:

- **L**: the sum of all polyline lengths, return legs included; a retraced stretch counts each time.
- **X**: points where two cables meet in the open, once per point; legs meeting at their own node or hub don't count.
- **O**: for every stretch covered by k legs on the same line, (k − 1) × its length.
- **B**: direction changes at polyline vertices, at every node (in vs out) and at the hub; a reversal counts once.

Three rules are unclear in the slides (D3 in [`clarifying_questions.md`](clarifying_questions.md); #46 Q4, Q9), so `checker.metrics(hubs, c, reading=...)` counts them two ways:

- `reading="strict"`, the default: our checker mirror and the sidecar's `cost`. A T-touch and each end of a shared stretch count as crossings, overlap counts between different rings, and turns at nodes and the hub count as bends, so our J is never lower than the organisers' could be.
- `reading="lenient"`: X only for cables passing through each other, O only a ring's overlap with itself, B only turns inside a leg. L is the same.

The app's counting-rules toggle shows both. Every edge case (T-touches, divergence points, co-routed corners, collinear end touches, point cleanup) is in [`decision_conventions.md` §6](decision_conventions.md#6-metrics-our-checker-mirror-slides-6-7).
